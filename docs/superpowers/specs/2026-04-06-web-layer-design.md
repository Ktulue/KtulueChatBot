# KtulueChatBot Web Layer — Design Spec

**Date:** 2026-04-06
**Branch:** `feat/web-layer`
**Session:** Session 2 (per the validated office-hours plan)
**Status:** Awaiting user review

## Purpose

Wrap the existing personality-first CLI chatbot in a web interface so visitors to ktulue.com can chat with KtulueBot from their browser. This is the second of the planned 2-4 sessions to take the bot from CLI to deployed web experience. Deployment itself is explicitly out of scope for this session and will be handled separately.

## Goals

- Visitors can open a web page and have a streaming, multi-turn conversation with KtulueBot
- The chat experience matches the dark Ktulue brand aesthetic established by the existing landing page
- The bot's personality, knowledge base, and behavior remain identical to the CLI version — there is one source of truth for personality
- The architecture is deployment-agnostic and can be hosted anywhere that runs Python
- Errors stay friendly and in-character for visitors while exposing real diagnostics in server logs
- The CLI bot continues to work unchanged

## Non-Goals

- Production deployment (separate session)
- User accounts, authentication, or persistent cross-visit history
- Database integration
- Monitoring, alerting, or analytics infrastructure
- Automated tests for the frontend JavaScript
- A polished embeddable widget (the eventual landing-page pop-up is a future session)
- Pre-deciding the production URL structure (subdomain vs path)

## Architecture

A single FastAPI application that does two jobs from one process:

1. Serves static frontend files (HTML, CSS, JavaScript) from a `web/static/` directory at the root URL
2. Exposes a streaming chat endpoint at `POST /api/chat` that calls the existing personality system and streams Claude's response back via Server-Sent Events

Local development is one command (`uvicorn web.app:app --reload`) and one URL (`http://localhost:8000`). No separate frontend dev server, no CORS configuration, no build step.

The existing CLI (`main.py`) is left untouched. The web app imports and reuses `personality.py`, `deflections.py`, `github_client.py`, and the `knowledge/` directory. Personality lives in exactly one place.

## Components

### Backend: `web/app.py`

The entire backend lives in this single file. It is intentionally small.

**Startup work (runs once when the server boots):**
- Load environment variables via `python-dotenv`
- Build the system prompt by calling `personality.build_system_prompt()` — the same function the CLI uses. Doing this at startup (not per request) means every chat starts instantly and GitHub repos are not refetched on every message.
- Create one Anthropic client instance to be reused across all requests
- Initialize Python's `logging` module with INFO-level output to stdout/stderr
- Initialize an in-memory session store: a plain `dict[str, list[dict]]` mapping session ID to message history

**Routes:**
- `GET /` — serves `web/static/index.html`
- `GET /static/{path}` — serves CSS, JS, and image files (handled by FastAPI's `StaticFiles` mount)
- `POST /api/chat` — the streaming chat endpoint (see below)

**The `POST /api/chat` endpoint:**

Accepts a JSON body with two required fields:
- `session_id` (string) — a UUID generated by the browser
- `message` (string, non-empty) — the user's text

Returns a streaming Server-Sent Events response (`text/event-stream`).

Logic:
1. Look up the session's history in the in-memory store. If it does not exist, create an empty list.
2. Append the user's message to the history.
3. Log the incoming message at INFO level: session ID, message text.
4. Call `client.messages.stream()` with the system prompt and history — same call shape as the CLI.
5. As tokens arrive from Claude, yield each one as an SSE `data:` event to the browser.
6. After streaming completes, append the full assistant response to the session history and log the full response at INFO level.
7. If anything goes wrong: log the real error at ERROR level with full traceback, send a friendly in-character SSE error event to the browser, and roll back the user message from session history so the failed turn does not poison future messages.

### Frontend error pool: `web/errors.py`

A small module containing one constant — a list of in-character error messages — and a helper to pick one. Modeled after `deflections.py`. Initial contents (final wording subject to refinement during implementation):

- "My brain just buffered. Hydrate while I reboot."
- "Connection's choppier than my Wi-Fi during a stream. Try that again?"
- "Something tripped a wire backstage. Give me a sec and try again."
- (3-5 more of similar voice)

The visitor never sees raw exception text, status codes, or stack traces. Errors stay on-brand.

### Frontend: `web/static/index.html`

A single HTML page with three regions:

1. **Header** — KTULUE logo (`logo.png`), the heading "KTULUE", "The Water Father" tagline. Visually consistent with the existing ktulue.com landing page so it feels like a natural extension of the same brand.
2. **Message area** — a scrollable container holding the conversation. Each message is either a user bubble (right-aligned) or a bot bubble (left-aligned). The typing indicator is its own bot-style bubble that gets shown and hidden.
3. **Input area** — a text input and a send button at the bottom. Pressing Enter sends. The send button and input are disabled while a response is in flight. Below the input, in italicized small text: *"Conversations are logged for quality, tuning, and diagnostic purposes only."*

### Frontend: `web/static/styles.css`

Pulls in the same dark aesthetic as the existing site:
- Same color palette as ktulue.com
- Geizer font for the header (matches the landing page)
- Body text and chat content use a readable web-safe font (Geizer is great for branding but rough for paragraphs of chat)
- Chat bubbles styled with rounded corners, clear visual distinction between user and bot
- Typing indicator: three animated dots that pulse
- Mobile-responsive: full-width on phones, max-width container on desktops
- Footer note (the logging disclosure) styled as small italicized text in a muted color

### Frontend: `web/static/chat.js`

Plain vanilla JavaScript. No framework, no build step, no npm.

**On page load:**
- Check `sessionStorage` for an existing `kchatbot_session_id`. If absent, generate a UUID v4 and store it. (`sessionStorage` is per-tab by design, which gives us the per-tab session isolation we want — two tabs are two independent conversations on the server side.)
- Wire up the send button click and Enter keypress on the input
- Show a brief hardcoded greeting message from the bot (no API call) so the page is not empty on first load

**When the user sends a message:**
1. Add the user's message to the chat area immediately (user-style bubble)
2. Disable the input and send button
3. Show the typing indicator (three pulsing dots in a bot-style bubble)
4. Open a `fetch()` call to `POST /api/chat` with the session ID and message
5. Read the response as a stream using the Fetch API's `ReadableStream` and parse SSE events
6. The moment the first token arrives: hide the typing indicator and create a new empty bot bubble
7. As more tokens arrive, append them to the bot bubble in real time
8. When the stream ends, re-enable the input and send button
9. If the stream errors out: hide the typing indicator, render the friendly in-character error bubble (received from the server's error event), re-enable the input

**Scroll behavior:**

The chat area expands as messages are added. **There is no auto-scroll.** The visitor stays in full control of their scroll position. Rationale: auto-scroll is genuinely hard to test correctly (timing windows, scroll-position tolerance, interaction with manual scrolling) and even well-known chat UIs get it wrong. Skipping it entirely eliminates a whole class of bugs and respects visitor attention. If usability testing later reveals visitors are missing new content, a non-intrusive "new message below" hint can be added in a follow-up session.

### Session storage

- Plain Python `dict` in memory: `{session_id: [{"role": str, "content": str}, ...]}`
- Lives in the FastAPI app process. Restart the server, all sessions reset. Acceptable for this stage.
- Each session is identified by a UUID generated by the browser and stored in `sessionStorage` (per-tab, auto-cleared when the tab closes — matches the "session-persistent" decision exactly).
- No cleanup logic. If memory ever becomes a concern, a max-age sweep can be added later. YAGNI.

## Error Handling and Logging

### What the visitor sees

Always in-character. Never technical. When something fails, an error message from `web/errors.py` appears in a bot-style bubble. The input remains usable so the visitor can immediately try again. No retry logic — automatic retries hide problems and complicate debugging.

### What the server logs

Python's built-in `logging` module, configured at app startup. Logs go to stdout/stderr. During local development, this means logs appear in the terminal where uvicorn is running. After deployment, hosting providers (Render, Railway, Fly, etc.) capture stdout/stderr and display it in their log viewer with no extra configuration on our side.

**INFO level (full conversation transcript):**
- Every incoming user message: session ID and message text
- Every successful bot response: session ID and full response text

**ERROR level (failures):**
- Anthropic API errors (rate limit, invalid key, server error, content policy): error type, session ID, the user message that triggered the failure, full exception details and traceback
- Network drop mid-stream: session ID, partial-failure context, traceback
- Unexpected exceptions: full traceback via top-level try/except in the endpoint

### Failure scenarios explicitly handled

| Scenario | Server-side action | Visitor sees |
|---|---|---|
| Anthropic API error | Log at ERROR. Roll back the user message from session history. Send friendly SSE error event. | In-character error bubble. Input re-enabled. |
| Network drop mid-stream | Log partial failure at ERROR. Roll back the user message from session history. | Whatever tokens arrived before the drop, followed by an in-character error bubble. Input re-enabled. |
| Invalid request body (missing field, wrong type, malformed JSON) | FastAPI's built-in `RequestValidationError` handler returns 422 automatically. No custom code needed. | Frontend treats any non-200 response as an error and shows the friendly bubble. |
| Unexpected exception | Top-level try/except logs full traceback at ERROR. Server keeps running. | In-character error bubble. Input re-enabled. |

### What we deliberately do not do

- No automatic retries
- No persistent error storage
- No alerting or monitoring infrastructure
- No PII scrubbing in logs (the disclosure under the input states logging is happening)
- No frontend error reporting back to the server (browser errors stay in the browser console)

## Privacy Disclosure

Below the input on the chat page, in italicized small text in a muted color: *"Conversations are logged for quality, tuning, and diagnostic purposes only."*

Visible but not intrusive. Honest about what is happening without being alarming.

## Testing Strategy

### Backend tests: `tests/test_web_app.py` (new)

Uses FastAPI's built-in `TestClient` (a thin wrapper around `httpx`, which is already in `requirements.txt`). No live server needed — the test client calls the FastAPI app directly in-process. The Anthropic client is mocked at every test boundary so tests run fast, free, and offline.

**Coverage:**

1. **Static file serving**
   - `GET /` returns 200 and contains expected HTML markers (page title, chat container)
   - `GET /static/styles.css` returns 200 with a CSS content type
   - `GET /static/chat.js` returns 200 with a JavaScript content type

2. **Chat endpoint — happy path**
   - `POST /api/chat` with a valid body returns 200 and a streaming response
   - The streamed response contains the mocked tokens
   - After the call, the session history contains both the user message and the assistant response

3. **Chat endpoint — session continuity**
   - Two requests with the same `session_id` build up a multi-turn history
   - Two requests with different `session_id`s have isolated histories (verifies per-tab isolation)

4. **Chat endpoint — validation errors**
   - Missing `message` field returns 422 (FastAPI default for `RequestValidationError`)
   - Missing `session_id` field returns 422
   - Empty `message` string: behavior to be decided during implementation (most likely 422 — empty messages are not useful and rejecting them is simpler)

5. **Chat endpoint — error handling**
   - When the mocked Anthropic call raises an API error, the SSE response contains a friendly in-character error event (not raw exception text)
   - The session history is rolled back: the user message that triggered the failure is removed
   - The error is logged at ERROR level (verified via pytest's `caplog` fixture)

6. **Logging behavior**
   - On success, the user message and bot response are logged at INFO level with the session ID
   - On failure, error details are logged at ERROR level with the session ID
   - Session IDs always appear in log records for correlation

### What is deliberately not tested

- **Frontend JavaScript.** Manual browser testing is faster than building a JS testing framework for ~150 lines of vanilla JS. Add tests later if the frontend grows significantly.
- **Real Anthropic API calls.** Always mocked. Real-world end-to-end testing happens manually by running the server and chatting with the bot.
- **CSS visual regression.** Out of scope. Eyeball it in the browser.

### Test runner

Same as today: `pytest` from the project root picks up everything in `tests/`. The existing CLI tests continue to run unchanged. No new pytest plugins, no new commands.

## How to Run

**Web server (new):**
```
uvicorn web.app:app --reload
```
Then open `http://localhost:8000` in a browser.

**CLI (unchanged):**
```
python main.py
```

The two are completely independent. Either or both can run at the same time in different terminals.
